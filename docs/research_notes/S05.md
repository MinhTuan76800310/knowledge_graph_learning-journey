# S05: Stanford CS520 — How to Create a Knowledge Graph?

- **Canonical URL:** https://web.stanford.edu/class/cs520/2020/notes/How_To_Create_A_Knowledge_Graph.html
- **Status:** Academic course notes (Stanford CS520, 2020)
- **Fetched:** 2026-08-25, HTTP 200
- **Used in:** Chapter 3 (schema design, relation-vs-property modeling, IRI design, identity links)

## Key Points

- You CAN start a KG with no upfront schema; "to the degree an upfront design is
  practical, it can significantly improve its usefulness" — schema design is
  useful but may evolve; population and schema can grow together.
- KG population inputs: structured data, semi-structured data, free text,
  images, human authoring. Structured sources require schema mapping + record
  linkage; unstructured sources require entity/relation extraction.
- Accuracy vs scale trade-off: web-scale IR tolerates imperfect accuracy;
  enterprise use needs near-perfect accuracy with human verification.
- RDF design = Linked Data principles: use URIs as names; use HTTP URIs so names
  are look-up-able; serve useful RDF/SPARQL on lookup; include links to other
  URIs.
- IRI design guidance: simple, stable, manageable; short and mnemonic; keep
  implementation details (.php/.asp) out; publisher must fully manage them.
- Reuse existing vocabularies (org:, skos:, schema.org); if minting a new
  vocabulary: documented, self-describing, versioned, multilingual, trusted
  publisher.
- Three link kinds: relationship links, IDENTITY LINKS (owl:sameAs is standard
  practice for stating two URI aliases refer to the same resource), vocabulary
  links (rdfs:subClassOf into external ontology).
- Property-graph design questions: property vs label vs separate node;
  when to introduce relationship properties; how to handle higher-arity
  relationships.
  - Label = class/set membership; use when membership is stable and frequently
    queried.
  - If class membership changes with time → neither label nor plain property
    fits; use a relation (optionally with time-valued relationship property).
  - Relationship properties: weights, confidence, provenance, metadata; if
    queries must filter heavily on them, consider reification (some engines do
    not index relationship properties).
  - Non-binary relationships → reification: create a node type for the relation,
    properties/edges for each argument (works for any arity, both models).

## Semantic Contract for Our Chapter 3

- Supports: "schema can be upfront, incremental, or evolved" (no claim that a
  KG requires a complete upfront schema).
- Supports: the property-vs-node-vs-label modeling spectrum and the
  time-varying-fact argument (capital since 1976).
- Supports: owl:sameAs as the standard identity-link mechanism between
  independently minted identifiers.
- The ML/algorithmic side of record linkage belongs to our Chapter 7, not 3.
