## Key Points

- Integrating structured sources into a KG faces two core problems:
  - **Schema mapping**: which relations/attributes in the input source
    correspond to which properties/relations in the KG schema.
  - **Record linkage**: inferring whether an incoming record and an existing KG
    entity are the same real-world entity.
- Schema mapping challenges: huge/semantically-poor source schemas
  (segment1, segment2), complex non-1:1 mappings with business logic, lack of
  training data → expect a largely manual, labor-intensive process.
- Mapping specification example: Datalog-style rules from source tables to
  target triples; a source identifier constant (vendor_1/vendor_2) records
  provenance of each mapped fact.
- "It may not make sense to reuse the identifiers from the source databases" —
  minting new KG identifiers is common; existing equivalent objects must then
  be detected (record linkage).
- Bootstrapping schema mappings: linguistic matching (exact/canonicalized
  names, synonyms/hypernyms, substring/pronunciation, description similarity),
  instance-based matching (datatype inference from values), constraint-based
  matching (uniqueness + numeric ⇒ candidate identifier). All inexact —
  bootstrap only; human experts must verify.
- Record linkage example: "AB Corporation / New York / NY" vs "ABC / New York /
  NY"; "Prolific Consulting Inc." vs "Prolific Consulting". Inexact inference,
  human validation required.
- Pipeline: **blocking** (cheap candidate selection) then **matching**
  (pairwise precise comparison); similarity functions (exact, Jaccard, overlap,
  cosine, edit distance); learned rules + active learning at industrial scale.
